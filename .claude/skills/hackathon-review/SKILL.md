# hackathon-review skill

ハッカソン用コードのレビューを行う。判断基準は「本番運用の理想形」ではなく **「締切までに動き、デモが壊れず、チームメンバーが読める」** かどうか。

## モード判定

引数（PR番号 or URL）があるかで動作を分ける。

- **引数あり**（例: `/hackathon-review 42`、`/hackathon-review https://github.com/owner/repo/pull/42`）
  → **PRモード**。`gh pr view` / `gh pr diff` で差分・メタデータ・既存コメントを取得してレビューする。
- **引数なし**（例: `/hackathon-review`）
  → **ローカルモード**。`git diff`（未ステージ含む）と直近コミットの差分をレビューし、結果を会話に返す。

**重要（誤投稿防止）**: GitHubへの投稿は、レビュー結果を提示してユーザーが明示的に承認するまで**絶対に行わない**。承認前は必ずターミナル/会話への「下書き」出力に留める。

---

## 大原則（すべての指摘の上位にある判断軸）

1. **動く > 綺麗**。デモを壊すバグ・例外は最優先。命名やスタイルは最後。
2. **over-engineeringを積極的に弾く**。「今のMVPに要らない汎用化・抽象化・将来対応」は指摘して削る方向に倒す。ハッカソンでは*今解くべき問題だけ*を解く。
3. **スタイルの好みでブロックしない**。個人的な好みは `🟢 NIT` を付け、ブロック理由にしない。
4. **良い所も言う**。設計判断が上手い箇所、コメントの追加漏れを綺麗に埋めた箇所などは短く褒める（チームの士気とレビューの受け入れやすさに効く）。
5. **指摘は必ず理由と直し方をセットにする**。「なぜ問題か」＋「どう直すか（できれば suggestion ブロック）」。指摘だけ投げない。

---

## 重大度タグ（すべての指摘に必ず1つ付ける）

| タグ | 意味 | 対応の目安 |
|------|------|-----------|
| 🔴 `BLOCKER` | デモを壊す / 起動しない / 秘密情報が漏れる | マージ前に必ず直す |
| 🟠 `MUST` | 明確なバグ・データ不整合・エッジケース欠落 | マージ前に直す |
| 🟡 `SHOULD` | 直すと確実に良くなるが、動作は壊れない | 時間があれば直す |
| 🟢 `NIT` | スタイル・命名の好み。ブロックしない | 任意 |
| 💡 `LATER` | 良い改善案だが**今のハッカソンではやらない**（over-engineering回避のための明示的な棚上げ） | ハッカソン後の宿題に回す |

`💡 LATER` を積極的に使うこと。「これは本番なら直すべきだが今はスコープ外」を明示的に切り分けるのが、締切のある開発でのレビューの肝。

## レビュー観点

以下を順に見る。該当しない項目は飛ばしてよい。

### 1. 動作・正しさ（最重要）
- 意図通りに動くか。エッジケース（null / 空配列 / 空文字 / 境界値 / タイムアウト / ネットワーク失敗）を落としていないか。
- 例外時にアプリ全体（＝デモ）が落ちないか。エラーが握り潰されて無言で失敗していないか。

### 2. セキュリティ（公開リポジトリなら 🔴 前提で見る）
- **APIキー・トークン・シークレットのハードコードや `.env` のコミット** → 即 `🔴 BLOCKER`。
- OAuthトークン・セッションCookieの扱い（スコープ最小か、httpOnly/暗号化されているか）。
- 外部入力（メール本文・ユーザー入力）をそのままプロンプトやクエリに埋めていないか（injection）。

### 3. LLMエージェント特有（Gemini / Vertex AI）
- **LLM応答のパース**: JSON前提の箇所で、モデルが崩れた出力を返したときに落ちないか。パース失敗のフォールバックがあるか。
- **プロンプト**: system/userの責務が混ざっていないか。ハードコードされた長大プロンプトが可読性を殺していないか（切り出し提案は `🟡 SHOULD`）。
- **二段エージェント（同定役→反証役）の境界**: 反証役に同定役の結論が漏れて追認になっていないか。逸脱層が「似てるのに違う一点」を本当に見ているか。← Crowの堀なので重点的に。
- **コスト/レイテンシ**: 不要なLLM呼び出しのループ、キャッシュ可能なのに毎回叩いている箇所。ただし「体感品質のための意図的なレイテンシ」は指摘しない（設計判断として尊重）。
- **承認ゲート**: 学習/書き込みの入口に人間の承認が挟まっているか。自動で状態を書き換えていないか。

### 4. Next.js特有
- **サーバー/クライアント境界**: `"use client"` の付け忘れ／付けすぎ。サーバー専用のキーがクライアントバンドルに載っていないか（`NEXT_PUBLIC_` の誤用は `🔴`）。
- Server Action / Route Handler の入力バリデーション。
- 環境変数がクライアントに漏れていないか。

### 5. 保守性・可読性（チーム開発の観点）
- **他のメンバーが読んで理解できるか**。理解に詰まる箇所は、それ自体が指摘対象（将来バグを生む複雑さ）。
- 関数/コンポーネントが大きすぎないか、責務が多すぎないか。
- コメントは **WHY（なぜ存在するか）** を書いているか。WHAT（何をしているか）の冗長コメントは削る方向。

### 6. テスト
- ハッカソンでは網羅は求めない。ただし**コアロジック（Crowなら逸脱判定、KangaL系ならレバースコアリング）**には最小限の検証があるか。
- 「デモで必ず通る経路」が壊れていないか。

---

## 「やらない」ことのチェック（over-engineering検出）

以下を見つけたら `💡 LATER` か `🟡 SHOULD` で削減提案する:
- 今使っていない汎用インターフェース・抽象基底クラス・設定の外部化
- 起きるか分からない将来ケースへの分岐
- MVPに不要なリトライ/キュー/キャッシュ層の作り込み
- 1箇所でしか使わないのに切り出された過剰なユーティリティ

## 出力フォーマット

```
## レビュー結果: <PR番号 or ローカル差分>

### サマリ
<2〜3行。マージ可否の見立てと、🔴🟠の件数>

### 指摘
- 🔴 BLOCKER `path/to/file.ts:42`
  <何が問題か> / <どう直すか>
- 🟠 MUST `path/to/file.ts:88`
  ...
- 🟡 SHOULD ...
- 🟢 NIT ...
- 💡 LATER ...

### 良かった点
- <設計判断や綺麗な実装を1〜2個>

### 判定
✅ 承認可 / 🔁 要修正（🔴🟠 が残っている間はマージしない）
```

指摘が0件のカテゴリは省略してよい。🔴🟠 が1件でもあれば判定は「🔁 要修正」。

## GitHubへの投稿（PRモードで、ユーザー承認後のみ）

1. まず上記フォーマットで下書きを提示し、投稿するか確認する。
2. 承認されたら `gh` でインラインコメント付きレビューを作成する。重大度タグは各コメント本文の先頭に付ける（例: `🟠 MUST: ...`）。
3. 直せる指摘には suggestion ブロックを添える:
   ````
   ```suggestion
   <修正後のコード>
   ```
   ````
4. 最終の event は原則 `COMMENT`（人間が最終マージを承認する運用）。`APPROVE` / `REQUEST_CHANGES` はユーザーが明示的に指示したときのみ。

## 運用メモ

- このskillは一次スクリーニング。設計意図・ビジネスロジックの妥当性・ピッチ観点は人間（＝あなた）が最終判断する。
- 見逃したバグや新しい落とし穴に気づいたら、この SKILL.md の観点に追記して育てる（同じ指摘を二度させない）。
- チームで使う場合は `.claude/skills/hackathon-review/SKILL.md` としてリポジトリにコミットすれば、メンバー全員が同じ観点でレビューできる。
